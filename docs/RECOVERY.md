# Recovery — wipe and restore

This repo never manages BIOS/firmware, the kernel, the NVIDIA driver, CUDA, or
the vendor OS image. Recover the platform layer through ASUS's (or NVIDIA's,
for a Founders Edition box) own recovery path first; this document starts
from a freshly reinstalled, healthy OS.

## Before you wipe — what's worth backing up

```
/etc/spark-ai-stack/secrets.env     # root:root 0600 -- sudo cp it somewhere safe (encrypted!)
~/ai-data/models/gguf/              # large local GGUF files (deepseek-v4-flash + drafter, etc.)
~/ai-data/huggingface/               # HF cache -- large, re-fetchable, back up only to save re-download time
~/ai-data/state/evals/               # lm-eval history (evals/lm-eval/compare.py needs this to diff against)
docker volume: spark-ai-pgdata        # litellm's postgres data
docker volume: spark-ai-openwebui     # openwebui's chat history / sqlite db
```

Everything else (`~/code/spark-ai-stack` itself, `/etc/spark-ai-stack/*`
other than `secrets.env`, `/run/spark-ai-stack/*`, `/var/lib/spark-ai-stack/*`)
is either in git or fully regenerated by `bootstrap.sh` + `sync` +
`modelctl fetch`. Docker volumes:

```bash
sudo docker run --rm -v spark-ai-pgdata:/src:ro -v /path/to/backup/pgdata:/dst alpine cp -a /src/. /dst/
sudo docker run --rm -v spark-ai-openwebui:/src:ro -v /path/to/backup/openwebui:/dst alpine cp -a /src/. /dst/
```

## Idempotency contract

`bootstrap.sh` and `sudo spark-ai-ctl sync` are both safe to re-run at any
time — every step checks current state before acting (`bootstrap.sh` never
reinstalls an already-present package or re-downloads an already-adopted
GGUF; `sync` only copies files that actually differ, and prints "unchanged"
for the rest). None of the steps below are destructive to re-run if
interrupted; just run the same command again.

## Restore runbook

Verify after every step before moving to the next — this stack fails loud and
early rather than silently continuing on a bad platform.

### 1. Reinstall the NVIDIA OS base

Follow the vendor's recovery image for your exact hardware (ASUS Ascent GX10
vs. NVIDIA DGX Spark Founders Edition — do not cross them). This erases the
internal SSD.

```bash
uname -m                 # verify: aarch64
nvidia-smi                # verify: GB10 visible, driver loaded
nvcc --version            # verify: CUDA 13.x
cat /etc/os-release        # verify: Ubuntu 24.04
```

### 2. `tailscale up`

```bash
sudo tailscale up          # interactive login
tailscale status            # verify: this node shows up, has a MagicDNS name
```

### 3. Clone the repo

```bash
git clone <this-repo-url> ~/code/spark-ai-stack
cd ~/code/spark-ai-stack
git log -1                 # verify: expected commit/branch
```

### 4. `sudo ./bootstrap.sh`

```bash
sudo ./bootstrap.sh
```

Verify:

```bash
command -v spark-ai-ctl && spark-ai-ctl --help >/dev/null 2>&1 || sudo spark-ai-ctl core-ps
sudo visudo -cf /etc/sudoers.d/spark-ai-stack     # verify: parses ok
systemctl is-enabled spark-ai-core.service spark-ai-boot-model.service  # verify: enabled
ls -l /etc/spark-ai-stack/secrets.env              # verify: root:root 0600
```

`bootstrap.sh` already ran `secrets-init` and an initial `sync --yes` for
you — every key except `HF_TOKEN` is already populated with a fresh random
value at this point.

### 5. Restore `HF_TOKEN`

Two options:

**(a) Hand-edit** (fresh token, or you don't have last time's backup):

```bash
sudoedit /etc/spark-ai-stack/secrets.env    # set HF_TOKEN=hf_...
sudo spark-ai-ctl secrets-init               # re-derive env.d/*.env; never overwrites HF_TOKEN
```

**(b) Restore from a backed-up `secrets.env`** (recovers every key, not just
`HF_TOKEN` — skips generating new random secrets for the others too, which
matters if any external client already has the old `LITELLM_MASTER_KEY`):

```bash
sudo cp /path/to/backup/secrets.env /etc/spark-ai-stack/secrets.env
sudo chmod 0600 /etc/spark-ai-stack/secrets.env
sudo chown root:root /etc/spark-ai-stack/secrets.env
sudo spark-ai-ctl secrets-init               # re-derive env.d/*.env from the restored file
```

Verify:

```bash
sudo spark-ai-ctl secrets-status    # verify: every key shows SET=yes (name/length only, never values)
```

### 6. `sudo spark-ai-ctl sync`

Already ran once inside `bootstrap.sh`; re-run explicitly to confirm nothing
changed since (or to review a diff if the repo has moved past what
bootstrap synced):

```bash
sudo spark-ai-ctl sync
```

Verify: `bin/doctor` should report every `sync_*` check as `PASS`.

### 7. `sparkctl core up`

```bash
bin/sparkctl core up
bin/sparkctl core status
```

Verify:

```bash
curl -fsS http://127.0.0.1:4000/health/readiness
curl -fsS http://127.0.0.1:3000/ >/dev/null && echo openwebui ok
curl -fsS 'http://127.0.0.1:8888/search?q=test&format=json' | grep -q results && echo searxng ok
```

If restoring `spark-ai-pgdata`/`spark-ai-openwebui` from backup, do it before
this step (`docker volume create` the named volume, then the reverse of the
copy command in the backup section above, then `core up`).

### 8. `modelctl fetch <models>` (or restore `~/ai-data` from backup)

```bash
# fastest if you have a backup:
rsync -a /path/to/backup/gguf/ ~/ai-data/models/gguf/
rsync -a /path/to/backup/huggingface/ ~/ai-data/huggingface/
rsync -a /path/to/backup/evals/ ~/ai-data/state/evals/

# otherwise, re-fetch from source:
bin/modelctl fetch qwen3.6-35b
bin/modelctl fetch deepseek-v4-flash   # GGUF + drafter, verified by sha256 in config/models.yaml
```

Verify:

```bash
bin/modelctl verify all        # sha256/snapshot-dir checks for every catalog entry you fetched
```

### 9. `doctor` expectations

```bash
bin/doctor --capture-baseline   # idle, core up, nothing active yet -- do this BEFORE activating
bin/doctor
```

At this point, expect: `platform_arch` PASS, `os_release` PASS, `cuda_13`
PASS, `nvidia_driver` PASS, `mem_baseline` PASS (baseline just captured),
`disk_free` PASS, `secrets_status` PASS, `loopback_boundary` PASS,
`docker_group_membership` WARN (until `--harden` runs — expected pre-cutover
and immediately post-recovery), every `sync_*` PASS, `core_litellm`/
`core_openwebui`/`core_searxng` PASS, `active_models` WARN ("no model
currently active" — expected before step 10), `tailscale_serve` WARN (until
step 11), `image_digests` PASS or WARN per whatever's pinned in
`config/versions.lock.yaml` at the time. There is no `--full` flag on
`bin/doctor` — `bin/modelctl sanity <model>` is the deeper per-model check,
run after activation.

Activate the boot model, then re-check:

```bash
bin/modelctl activate qwen3.6-35b
bin/doctor   # active_models should now PASS
```

### 10. `tailscale-configure`

```bash
bin/sparkctl tailscale-configure          # dry-run first -- prints what it would do
bin/sparkctl tailscale-configure --yes    # applies: resets Serve, re-adds /, /v1, /search
tailscale serve status
```

Verify from another tailnet node:

```bash
curl -i https://<magicdns-name>/v1/models          # expect 401 (no key)
curl -fsS -H "Authorization: Bearer $LITELLM_MASTER_KEY" https://<magicdns-name>/v1/models
curl -fsS 'https://<magicdns-name>/search/?q=test&format=json'
```

## Full verification pass

```bash
bin/doctor
bin/sparkctl acceptance   # needs LITELLM_MASTER_KEY exported; see docs/OPERATIONS.md
```

Both should report clean before you consider recovery complete.
